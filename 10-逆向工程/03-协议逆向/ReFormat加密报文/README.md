# ReFormat：报文被加密时，先把明文缓冲区找出来

> Z. Wang, X. Jiang, W. Cui, X. Wang, M. Grace, *ReFormat: Automatic Reverse Engineering of Encrypted Messages*, **ESORICS 2009**（LNCS 5789, pp. 200–215）。此前所有协议逆向方法都只能处理**明文**通信；ReFormat 补上的正是这一环——找出解密后的明文缓冲区，然后**把它交给 AutoFormat/Tupni/Polyglot**，于是"明文能做的，加密也能做"。

## 一、简介

加密带来的三个具体困难（论文 §2）：

1. **装明文的缓冲区事先未知** —— 它可能动态分配在堆或栈上。明文时代可以直接盯住 `sys_read` 关联的缓冲区，加密时代不行；
2. **候选缓冲区极多** —— 用污点分析只保留被污染的缓冲区后，实测仍有**数十甚至上百个**（论文 Table 2）；
3. **明文缓冲区可能只存在很短一段时间** —— 处理完就被丢弃或复用。

ReFormat 的四步：执行监视 → **相位划分器** → **数据生命周期分析** → 格式分析（本 demo 复现中间两步，第四步直接复用 AutoFormat）。

## 二、原理详解

### 2.1 基本观察：两个相位的指令分布显著不同（§3.1，Table 1）

现有加密算法（Triple-DES、AES、RC4）含**大量算术与位运算**，而且会作用到原始报文的**每一个字节**；正常协议处理则显著更少。论文用 OpenSSL 里的实现与一批明文处理程序实测对照：

| 加密/报文类型 | 报文大小 | 算术+位运算 | 总指令 | 占比 |
| --- | --- | --- | --- | --- |
| DES | 2K | 68921 | 69112 | **99.72%** |
| CAST | 2K | 18917 | 21225 | **89.13%** |
| RC4 | 2K | 2709 | 3042 | **89.05%** |
| AES | 2K | 6892 | 8475 | **81.32%** |
| HTTP request | 107 | 429 | 3227 | 13.29% |
| FTP port | 28 | 421 | 5898 | 7.14% |
| DNS response | 46 | 223 | 1687 | 13.22% |
| RPC bind | 164 | 186 | 2342 | 7.94% |
| JPEG | 3224 | 1112 | 12898 | 8.62% |
| BMP | 3126 | 229 | 956 | **23.95%** |

一句话概括：**解密 > 80%，明文处理 < 25%**。本 demo 把这两条不等式写成断言。

### 2.2 相位划分器 Phase Profiler（§3.3）

目标是找**第一条相位与第二相位的分界**（第一条 = 消息解密；后三条 = 处理明文、生成响应、加密响应）。

**为什么不能直接用累计百分比**：应用程序**最后还要加密输出报文**，那段同样充满算术与位运算，累计百分比会重新抬升。但加密输出之前，"处理明文 + 生成明文响应"会引入大量非算术非位运算指令，因此**解密期间的累计百分比会是整个轨迹的峰值**。

两步走：

**Step I** —— 算累计百分比（第 n 条处 = 前 n 条里算术与位运算指令的占比），取**最大值所在指令**与**最小值所在指令**，跃迁点必在两者之间；

**Step II** —— 在这个搜索范围内，按**函数片段**重新算**片段级**百分比，取**最后一个**超过阈值的片段作为**跃迁函数**，其最后一条指令即**跃迁点**。

**函数片段** = 连续、属于同一函数、**且在同一运行期栈帧下**执行的指令。父函数 A 调用 B 再返回会切出 `FA1 / FB / FA2` 三个片段；每条指令**有且仅属于一个片段**。

用片段级而非累计级的原因（论文原文）：**真正做解密的函数片段，其片段级百分比才高**。阈值取 **50%**，论文脚注说"25% 到 80% 之间的任何值效果都一样"——本 demo 断言 25/50/80 给出同一个跃迁片段，且阈值若高过所有解密片段（97%）则无片段达标。

> **一个必要的降级路径**：若解密与处理写在同一个大函数里（没有函数边界），论文改用**滑动窗口**当"伪片段"来计算百分比；但论文自己没在评测中遇到这种情况，因此**没有探索窗口大小的选择**。

### 2.3 数据生命周期分析 Data Lifetime Analyzer（§3.4）

思路：**明文缓冲区必然是"在解密阶段被写、在正常处理阶段被读"的那块内存**。

活性（liveness）定义分两个相位，规则**不同**：

| 相位 | 事件 | 结果 |
| --- | --- | --- |
| 启动 | 为全局变量预分配的缓冲区 | live |
| 解密 | 在堆/栈上分配 | live |
| 解密 | 被释放 | 失效 |
| **处理** | 被释放 | 失效 |
| **处理** | **被写** | 失效（内容不再来自解密阶段） |
| **处理** | **被读** | 失效（只关心**第一次**读） |

三步：

1. **write set** = 解密阶段被写过、且进入处理阶段时仍 live 的缓冲区；
2. **read set** = 在处理阶段**首次被读**时仍 live 的缓冲区；
3. 二者**交集**即装明文的缓冲区。

- 交集只有一块 → 直接作为明文输入交给格式分析；
- 交集有多块 → 按**首次读取的时序**排序，当作**一块虚拟缓冲区**（拼起来才是完整明文）。

本 demo 的夹具里 `write set = {A, C, D}`（B 在处理阶段前已释放、E 从未被写）、`read set = {A, C, F}`（F 是处理阶段新建的），交集 `{A, C}` 按首次读取时序排成 `[C, A]`；另一条断言显示 D 若在进入处理阶段后**先被写**，即使之后再读也进不了交集。

### 2.4 格式分析（§3.1 第 4 步）

论文原型直接用 **AutoFormat** 作为格式分析器，并说明"其他系统（Polyglot / Tupni / Dispatcher）同样适用"——这正是 ReFormat 的定位：**它不重复造格式推断，只负责把明文挖出来**。

## 七、性能边界与注意事项

- **阈值 50% 是实测值**，不是理论值；其有效区间 25%~80% 也来自论文在 OpenSSL 上的实测，换一套密码库需要重新标定。
- **解码依赖能被插桩的二进制**（论文原型基于 Valgrind 3.2.3）。
- **假设报文边界可辨识**，一次轨迹只处理一条输入报文。
- **处理阶段的"首次读即失效"是硬规则**：若明文缓冲区的头几个字节在解密阶段后先被"写"覆盖过，就再也找不回来。
- **滑动窗口降级路径未被评测**（2.2）。

## 八、常见坑（本 demo 实跑暴露）

1. **不能只用累计百分比**——末尾的输出加密会把它重新抬起来，必须由函数片段收口；
2. **函数片段要同时比较函数名与栈帧 id**：同名函数被递归调用或被不同调用点调用时，栈帧不同，必须切开；
3. **累计百分比的首条指令决定极值**：若第一条是算术指令，累计从 100% 起，全局最大值会落在 index 0 —— 这不影响结果（搜索范围仍覆盖解密段），但会让"最大值在解密阶段"这句话的证明变得微妙；
4. **write set 必须在"进入处理阶段"这一时刻快照活性**，否则把处理阶段的读写混进去会污染交集。
