# 游戏网关(Gateway / Connector)

> 用「连接层 + 路由层」把玩家的长连接与游戏实例解耦:玩家只连一个入口,消息按**类型**找服务、按 **uid** 找实例;
> 内部服务要主动推送时,靠会话表里记录**网关 id** 找回长连接。
> 本 demo 把 4 件事全部量化:路由表、实例选择(取模 vs 一致性哈希)、会话表与推送回程、网关故障重建。

本目录含 3 种语言实现(**Python / C / Go**),输出完全一致,可交叉验证。

---

## 一、要解决什么问题

玩家与服务器之间是**长连接**。如果让客户端直连游戏服,会遇到三个硬伤:

1. **单点与容量**:一台游戏服承载的连接数有限(单机 fd 上限、内存),实例一挂玩家全掉;
2. **连接不可复用**:换房间/换场景 = 换机 = 断线重连,额外 RTT + 重登录,体验抖动;
3. **鉴权/限流/保活散落各处**:每个业务服都要重复实现一遍。

业界通用解是加一层**网关**:客户端统一连网关,网关做鉴权、限流、心跳保活;业务服只处理业务逻辑。
此时网关必须回答两个问题(对应一次消息转发的两步查找):

```
client ── msg(0x20, uid=0) ──▶ 网关
                                  │ ① 按消息类型查路由表: 0x20 -> "room"
                                  │ ② 按 uid 选实例:        0 % 8 -> room#0
                                  ▼
                               room 服务 room#0
```

再加两个工程问题:

- **③ 主动推送**:房间邀请、聊天、被踢等是服务端主动下发的。服务不知道玩家挂在哪台网关上,
  因此网关**转发时必须把自身 id 带进上下文**,服务 push 时才能找回那条长连接。
- **④ 无状态化**:网关自己也会宕机、也要扩缩容。若要水平扩容,网关进程内就不能存"必须是这台机器上"的状态,
  或者允许状态重建 —— 代价是客户端要能重连并重建会话。

Azure 架构中心把这类做法归纳为 **Gateway Routing pattern**,并列出三类典型场景:
多个互不相同的服务 / 同一服务的多个实例 / 同一服务的多个版本,统一收敛到一个端点
(`Expose multiple services on a single endpoint and route to the appropriate service based on the request`)。

## 二、消息路由表(第一步查找)

```
0x01 0x02 -> login      0x10 0x11 -> match      0x20 0x21 0x22 -> room
0x30 0x31 -> battle     0x40 0x41 -> chat       0x50 -> rank      0x60 0x61 -> inventory
```

14 个消息类型 -> 7 个服务。**未知类型必须被拒绝**,而不是"就近投一个":
demo 里 `route(0x99)` 返回空并计入 `rejected_unknown`,这样客户端版本不一致时能在网关侧看到归类错误,
而不是把流量打到语义不匹配的服务里、让业务侧去猜。

## 三、实例选择:uid 取模 vs 一致性哈希(第二步查找)

同一服务会部署多实例,选实例要让**同一个 uid 打同一个实例**(粘性),否则玩家状态会被反复搬迁。

- **取模** `uid % n`:零成本、绝对均匀,但 `n` 一变,几乎全员重映射。
- **一致性哈希**:节点与虚拟节点按哈希排在 0..2^32 的环上,取 uid 的**顺时针后继**;
  增删节点只影响相邻区间,迁移量约 `1/n`。

demo 实测(20000 个 uid):

| 操作 | 取模重映射 | 一致性哈希重映射 | 理论下限 1/max |
| --- | --- | --- | --- |
| 扩容 8 -> 9 | **88.88%** | **11.85%** | 11.11% |
| 缩容 9 -> 8 | **88.88%** | **11.85%** | 11.11% |

niginx 官方文档对同一问题给了完全一致的判断:普通 `hash` 方法下
`adding or removing a server from the group may result in remapping most of the keys to different servers`;
而 `hash $key consistent` 使用 ketama 一致哈希,`ensures that only a few keys will be remapped to different
servers when a server is added to or removed from the group`。

**虚拟节点数**决定负载均匀度(哈希环天然会出现区间大小不均):

| 每节点虚拟节点数 | 160(ketama 默认) | 256 | **512(本 demo)** | 1024 |
| --- | --- | --- | --- | --- |
| 8 节点最大负载偏差 | 43.92% | 40.96% | **25.72%** | 23.52% |

对照:取模法偏差恒为 **0.00%**(但重映射率 88.88%)。可见一致哈希是拿「少量不均匀」换「少量迁移」,
虚拟节点数越大越接近取模的均匀度,但收益递减(512 -> 1024 只降 2.2 个百分点,内存翻倍)。

## 四、会话表、推送回程与 TTL

会话表 `uid -> (网关 id, 服务实例, 最后活跃时间)`:

- **绑定**:`connect` 决定连接落在哪台网关(按 uid 取模,避免集中在刚重启的节点上);
- **推送回程**:`push(uid, payload)` 先查会话表拿到网关 id,再看该网关是否还在集群里、
  连接是否还挂在它上面 —— 三者齐备才返回 `gw0->0:invite`,否则推送失败(等客户端重连);
- **TTL**:`SESSION_TTL = 300s`,客户端心跳 `30s`;**必须靠业务消息刷新**,而不是"连接还在"就认为活跃。

demo 实测:6 分钟后(`30s × 12`),期间发过心跳的 3 个会话保留、未刷新的 3 个被回收,剩 3 条。
`SESSION_TTL / HEARTBEAT = 10`,所以"心跳间隔 × 12"足以判定过期,这个余量用来容忍偶发丢包。

## 五、网关故障:断连重连 + 会话重建

4 台网关、40 条连接,gw1 下线:

```
gw1 下线: 断开 10 条连接, 会话记录作废; 剩余网关 [gw0, gw2, gw3]
客户端重连并重建会话: 10 个 (模数由 4 变 3, 落点必然变化)
```

两个结论:

1. 受害连接**必须**重连 —— 连接是 TCP 层的,网关进程没了连接就断了,没有"迁移连接"这种操作;
2. 重连后**落点必然变化**(4 -> 3 取模不同),所以会话绑定只能重建,不能指望原样恢复。
   推论:网关要么**无状态**(会话放 Redis/etcd 等外部存储),要么接受重连重建。
   Azure 文档也提示网关会引入单点与瓶颈,需要考虑冗余与过载时的级联失败。

## 六、三种语言实现对照

| 语言 | 文件 | 要点 |
| --- | --- | --- |
| Python | `python/gateway.py` + `python/hashring.py` | 参考实现;`bisect` 做环上查找,`dict` 直接当会话表 |
| C | `c/gateway.c` + `c/hashring.{h,c}` | 手动数组管理环与二分查找;会话/连接用定长数组 + 交换删除 |
| Go | `go/hashring.go` + `go/gateway.go` + `go/selftest.go` | `sort.Search` 等价于 Python 的 `bisect_left`;`map[int]bool` 表连接集合 |

三种实现使用**同一个哈希**(FNV-1a 32 位)、**同一份路由表**、同一个环上取值规则
(第一个 `哈希 >= h` 的虚拟节点,越界回绕),所以 `uid` -> 实例的下标完全一致。

## 七、运行方式

```bash
python python/gateway.py                       # Python 3.10+
gcc -O2 -Wall -Wextra -pedantic c/gateway.c c/hashring.c -o gateway && ./gateway
cd go && go run .                              # Go 1.21+
```

三者都打印同样的四段自检,失败时退出码非 0。

## 八、性能边界

- 一次转发 = 1 次哈希表查找(路由表)+ 1 次整数取模或两条二分查找(环)+ 1 次会话表写入;
  实测阈值级开销,不是吞吐瓶颈;真实瓶颈在**连接数 × 心跳**带来的包量。
- 环内存:512 虚拟节点 × 节点数 × (4 字节哈希 + 节点引用) → 100 节点约 205 KB,可忽略;
  但**重建环是 O(V·N log(V·N))**,应在配置变更时重建一次并原子替换,不要每请求重建。
- 会话表会被"僵尸会话"撑大:TTL 300s + 心跳 30s 时,每条会话最多占 5 分钟;
  百万在线 ≈ 百万条会话记录,需要按 uid 分片或放外部存储。
- 取模法在"实例数固定"时性能与均匀度都优于一致哈希(0.00% 偏差),别为了时髦强行上环。

## 九、注意事项与常见坑

1. **未知消息类型不能乱投**:必须显式拒绝并计数,否则新老客户端混跑时故障会跑到业务服里才暴露。
2. **取模扩容 = 全员迁移**:88.88% 的玩家换实例。要扩容就两条路 —— 上一致哈希;
   或者把实例数取 2 的幂,把 `uid % n` 换 `uid & (n-1)`,倍增时只搬一半(扩容后仍保持取模的均匀度)。
3. **虚拟节点给少了等于没上环**:ketama 默认 160 点时 8 节点偏差 43.92%,比取模的 0.00% 差得多;
   demo 用 512 点压到 25.72%。节点数越少偏差越大,2~3 个节点时需格外注意。
4. **哈希 key 的字节表示必须跨语言一致**:别用语言相关的默认格式(如容器 `repr`、浮点 `%.g`)拼 key,
   否则同一 uid 在 Python 与 Go 里会落到不同实例;本 demo 统一 `"uid:%d"` 字符串 + 按 UTF-8 字节做 FNV-1a。
5. **转发时必须回传网关 id**:少了这一步,服务端 push 无处可去(本 demo 里 `push(99)` 直接失败),
   表现为"玩家在线但收不到邀请"这类难复现的 bug。
6. **会话 TTL 用"业务消息"刷新,不要用"连接存在"**:掉线但 TCP 未感知(拔网线、休眠)时,
   把连接当活跃会让会话表永远不回收;反过来 TTL 设太短会误杀挂机玩家。
7. **网关要无状态**:把会话只放网关内存,扩容/宕机就丢;demo 里 gw1 下线 10 条会话全作废并靠重连重建。
8. **网关自身是单点**:多实例 + 前置 L4/L7 负载均衡;监控转发延迟、拒绝数(未知类型)、
   会话回收量、重连风暴 —— 重连风暴是网关雪崩的典型起点(建议重连加退避抖动)。
9. **推送回程与连接归属要一起校验**:网关还在集群里但连接已不在(客户端刚漂到别的网关),
   不能按老网关推,否则消息发进空连接。
