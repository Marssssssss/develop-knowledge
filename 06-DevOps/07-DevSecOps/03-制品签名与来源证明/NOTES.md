# NOTES — demo573 口径说明与踩坑

## 一、为什么本 demo 的证据特别强

`python/p256.py` 是纯标准库实现的 P-256 ECDSA（RFC 6979 确定性 nonce），
自检里的 C1 断言要求它**逐字节复现 DSSE protocol.md 给出的官方 base64 签名**，
B0 断言要求 `d·G` 等于官方给出的公钥 (X, Y)。

两条都对上，说明实现里的点运算、nonce 生成、整数编码**全部**与官方一致 ——
这比「自己签自己验」强得多：自己签自己验在编码写反（比如 s 用错了模）时也会全绿。

## 二、口径说明（官方未给定量处，本 demo 选的读法）

1. **未知 bundle 版本的处理**：`sigstore_bundle.proto` 只说「客户端必须能接受此前定义的格式」，
   没说未知版本怎么办。本 demo 取「拒绝」，并在 `accept_bundle_media_type` 的注释里标注。
2. **`bits2int` 的裁剪**：RFC 6979 要求哈希位数超过 `qlen` 时右移取左 `qlen` 位。
   P-256 的 `qlen = 256`、SHA-256 输出也是 256 位，所以裁剪分支在本 demo 里**不会被触发**；
   实现保留它是为了不把「恰好相等」当通用规则。
3. **`e` 不做模 n 归约**：`u1 = e·w mod n`，先归约 `e` 与直接算结果相同，故实现里直接用
   `int.from_bytes(sha256(msg))`。

## 三、开发期修掉的问题

1. **A4b 是期望值算错**：原断言「官方 PAE 恰好含 4 个空格」，实际是 5 个 ——
   官方向量的 payload 本身就是 `"hello world"`，**里面带一个空格**。
   改用无空格的 `pae("t", b"x")` 来数分隔符（代码自始至终是对的）。
2. `go/dsse.go` 初版用了不存在的 `*bigInt` 与 `bytesToInt`，改成 `*big.Int`
   并把 `bytesToInt` 落在本文件里（同时补 `math/big` import）。

## 四、容易写反的断言

- **D5c 不能省**：只测「keyid 能过滤」不够，必须同时测「验签不依赖 keyid」，
   否则「实现把 keyid 当安全凭据」这个 bug 测不出来。
- **E2 是 (t,n) 语义的核心**：把同一签名复制两遍凑不出 t=2 —— 只测「两个不同密钥能过」
   是伪断言，任何实现都会过。
- **B2/B3 必须成对**：改 payload 失败说明 PAE 覆盖了 body，改 payloadType 失败说明
   覆盖了 type。只测前者会漏掉「实现忘了把 type 拼进 PAE」这类错误。
