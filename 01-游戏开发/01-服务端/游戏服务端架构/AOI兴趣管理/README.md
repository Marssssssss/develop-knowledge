# AOI 兴趣管理（九宫格）

## 简介

**AOI（Area Of Interest，感兴趣区域）** 是游戏服务端的**位置驱动消息过滤层**：把一个实体的「广播面」从整个场景收缩到它周围的一小块区域，只把该区域内的变化同步给它。MMO 里「玩家 C 站在旁边看到了 A 打 B，而远处的玩家 D 一无所知」就是 AOI 的直接产物。

关键概念：

| 概念 | 含义 |
| --- | --- |
| **观察者集合（Interest / Watcher List）** | 每个实体维护「谁看得见我」，A 攻击时按这张表下发，而不是遍历全场景 |
| **九宫格** | 地图切成等大正方形格子，实体视野 = 所在格 + 周围一圈（3×3） |
| **Enter / Leave / Move** | AOI 只有三种事件：进入视野、离开视野、在视野内更新 |
| **AOI 边界抖动** | 实体在视野边缘反复进出，导致客户端模型反复创建/销毁 |
| **滞回（hysteresis）** | 用「进入阈值 < 离开阈值」的双阈值消除抖动 |

历史背景：AOI 是随着 MMO 同屏人数上升而被迫出现的工程解。朴素方案（每次攻击遍历全场景算距离）在「1 次攻击要下发 4~5 个包、一刀打一片怪可能 10 个包」的量级下直接不可用，于是「空间换时间」的格子/链表结构成为标配。

## 原理详解

### 1. 核心数据结构

```
地图 40 x 30 格, 每格一个 list 存当前格内实体
cells[cy * W + cx] = [eid, ...]

九宫格 = 自身格 + 八邻格, 共 9 格 (VIEW = 1)
出界部分被裁剪 —— 地图边界即视野边界
```

### 2. 事件分发流程

实体位置变化时**只有一个入口**：对「旧九宫格集合 `old_nb`」与「新九宫格集合 `new_nb`」求差集。

```
old_nb = 9 个格子索引     new_nb = 9 个格子索引

(old_nb - new_nb)  -> Leave   这些格子里的人从此看不见我
(new_nb - old_nb)  -> Enter   这些格子里的人开始看得见我
(old_nb & new_nb)  -> Move    一直在视野内, 只同步位置变化
```

| 移动方式 | \|old−new\| | \|new−old\| | \|old∩new\| | 说明 |
| --- | --- | --- | --- | --- |
| 同格内微动 | 0 | 0 | 0 | 只给九宫格内所有人发 Move |
| 水平/垂直跨 1 格 | 3 | 3 | 6 | 少一列，多一列 |
| 对角跨 1 格 | 5 | 5 | 4 | 少 5 格、多 5 格，重叠只剩 2×2 |

> 本 demo 用程序断言了上表（`[自检 1]`），并单独验证了「三个格子组各自把消息发给谁」（`[自检 2]`）。

### 3. 关键实现细节

1. **先摘旧格、再插新格**：否则实体自己会被算成 `new_nb` 里的邻居，收到发给自己的 Move。
2. **广播时必须剔除 self**：`old ∩ new` 一定包含自己的新格子，不排除就会自收消息。
3. **入场时先入格再广播**：`enter()` 把 eid 写进格子后再取九宫格邻居，否则「刚进场的我」不在任何格里，拿不到观察者列表。
4. **同格内微动也要广播**：格子里有 5 个实体时，其中一个动一下，另外 4 个都必须收到 Move（`[自检 3]`）。

### 4. 边界抖动与滞回

纯九宫格的视野判定是**单阈值**的：进格就同步、出格就取消。实体卡在格子边界来回时：

```
gap = 0（单阈值: 进 <= 1.0 格, 出 > 1.0 格）
  抖动 400 次 -> Enter = 400, Leave = 400, Move = 0    ← 完全抖动

gap = 1（双阈值: 进 <= 1.0 格, 出 > 2.0 格）
  抖动 400 次 -> Enter = 0,   Leave = 0,   Move = 400  ← 抖动被消除
```

工程上的标准做法（本 demo 的 `HysteresisAOI` 就是它的最小模型）：

- 区分 `in_aoi` / `out_aoi` 两个距离，中间留一段 **gap**（注意 gap 是**格子数**不是世界距离）；
- 从最外层进入内圈才发 Enter；离开外圈才发 Leave；
- 十字链表的「哨兵节点」本质上也是同一思想：把阈值做成随实体移动的锚点。

### 5. 核心 API

| 方法 | 签名 | 语义 | 返回值 |
| --- | --- | --- | --- |
| `enter` | `(eid, x, y)` | 实体进场并广播自己的出现 | 无 |
| `move` | `(eid, x, y)` | 更新位置，必要时发 Leave/Enter/Move | `{leave, enter, common}` 三组格子索引；未跨格时三者皆空 |
| `leave` | `(eid)` | 实体退场，向九宫格内广播 Leave | 无 |
| `nb` | `(cx, cy, r)` | 取半径 r 的方形邻域格子索引 | 格子索引列表（已裁剪到地图内） |

## 对比 / 选型

| 方案 | 空间复杂度 | 查询视野 | 可变视野 | 大地图 | 三轴（3D） |
| --- | --- | --- | --- | --- | --- |
| **九宫格** | O(W·H) 预留，与人数无关 | O(9 格内实体) | 难（要按最大视野遍历） | 差（1024² 格也要预留 8 MB 指针） | 要变 27 宫格，膨胀到 GB 级 |
| **灯塔（大格）** | O(W·H)，格子更大 | O(4 格内实体) | 同九宫格 | 一般 | 一般 |
| **十字链表** | O(N)，与人数成正比 | O(链表遍历) | 天然支持（间距可变） | 好 | 加一条链表即可 |
| **四叉树** | O(N) | 查询省，**相邻格搜索麻烦** | 支持 | 好 | 支持 |

选型结论（综合各来源的共识）：

- 有经典 tile map、视野固定 → **九宫格**最省事，坐标直接就是格坐标；
- 大地图 + 可变视野（飞行/跳跃/swing 视野） + 三轴 → **十字链表**（kbengine 用的就是三轴十字链表）；
- 两者都怕**聚集**：十字链表在「多数实体 X 坐标相同」时退化成线性遍历，九宫格在「玩家全挤在一格」时退化成格内暴力遍历。

```python
# 跨格分支：差集决定事件类型（对应「原理详解 §2」）
old_nb, new_nb = set(self.nb(ox, oy)), set(self.nb(nx, ny))
leave, enter, common = old_nb - new_nb, new_nb - old_nb, old_nb & new_nb

# 先摘旧格 -> 再插新格：否则自己会被算作 new_nb 的邻居而收到发给自己的消息
self.cells[self.cell[eid]].remove(eid)
self.pos[eid] = (x, y)
nidx = self.idx_of(nx, ny)
self.cell[eid] = nidx
self.cells[nidx].append(eid)

for idx in leave:
    self._send("Leave", eid, self.cells.get(idx, ()))
# enter 集合可能包含自己刚进入的那一格（跨 >= 2 格时）
for idx in enter:
    self._send("Enter", eid, [e for e in self.cells.get(idx, ()) if e != eid])
for idx in common:
    self._send("Move", eid, [e for e in self.cells.get(idx, ()) if e != eid])
```

## 性能与边界

本 demo 实测（Python 3.13，40×30 格，300 实体 × 400 步随机游走，单格边长 1、步长 ±0.6）：

| 指标 | 朴素全场景广播 | 九宫格 AOI | 降幅 |
| --- | --- | --- | --- |
| 总消息条数 | 35,880,000 | 300,224 | **99.16%** |
| 每实体每步消息数 | 299.000 | **2.502** | — |

- 消息构成：Move 208,420 / Enter 45,914 / Leave 45,890 —— **Move 占 69%**，说明稳态下绝大多数是同格内与邻格的连续位置同步。
- 每实体每步 2.5 条 ≈ 9 格 × 密度（300 / 1200 = 0.25）× 邻域重叠修正，与格子密度线性相关。
- 复杂度：单次跨格 O(9) 找差集 + O(格内实体数) 广播；未跨格 O(9 + 格内实体数)。
- 内存：`cells` 需要 W·H 个列表头。1024×1024 格即使只存指针也要 `1024×1024×8 = 8 MB`；三轴变 27 宫格则膨胀到 8 GB 量级（所以三轴一般改用哈希表，代价是慢一点）。
- 视野若做成**圆形**：判定点是否在圆内要算平方，方形只需比大小，因此绝大多数实现用方形 AOI。

## 注意事项与常见坑

1. **跨格却把消息发给了自己** —— 现象：实体收到关于自己的 Move/Enter；原因：`common` 必然含自己的新格、`enter` 在跨 ≥2 格时也可能含；规避：广播时统一剔除 self（本 demo 的 C 版就专门断言了「含 eid + 观察者 = 2」）。
2. **先插新格再算差集** —— 现象：`new_nb` 里的自己把自己算成邻居；规避：**先摘旧格 → 算差集/插新格 → 广播**，或广播时统一剔除 self。
3. **入场顺序错** —— 现象：刚进场的实体拿不到周围人；规避：`enter()` 必须**先入格再取邻居**。
4. **边界抖动导致客户端模型闪烁** —— 现象：边界上的实体反复 Enter/Leave，客户端不停创建销毁模型；规避：双阈值滞回（gap），并在客户端侧对 Enter/Leave 做去抖。
5. **九宫格在玩家聚集时退化** —— 现象：一格挤了几百人，Move 广播变成格内暴力遍历；规避：分线/分层，或改用链表类算法。
6. **十字链表怕坐标聚集** —— 现象：所有实体 X 坐标相同时，链表遍历退化成 O(N)；规避：加地标索引节点 + 二分定位。
7. **视野半径与格子大小必须一起调** —— 格子大小通常取约 1/4 个屏幕，9 格略大于一屏；格子太小 → 事件风暴，格子太大 → 过滤失效。
8. **AOI 更新时机** —— 定时器批量同步（省 CPU，但技能位移可能丢帧）vs 位置变化立即更新（可控但开销大）；生产上常见「移动由定时器按速度推算 + 技能等强同步动作立即更新」的混合方案。
