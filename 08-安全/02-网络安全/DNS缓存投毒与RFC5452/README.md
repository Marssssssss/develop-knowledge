# DNS 缓存投毒（伪造应答）与 RFC 5452 的组合难度

## 简介

DNS 解析器用**源/目的地址 + 源/目的端口 + Query ID** 这五个量把应答匹配到查询，全部字段一共只有 16 位 ID 是随机量。2008 年的 Kaminsky 缺陷把这个老问题变成了可实际利用的攻击：攻击者不需要等目标域的 TTL 到期，而是**主动触发**查询（查询 `random123.example.com`），于是在应答返回前有一个「机会窗口」，往里面灌伪造应答即可。

RFC 5452《Measures for Making DNS More Resilient against Forged Answers》（2009）在 DNSSEC 全面铺开之前的过渡期给出了量化模型与缓解措施。本 demo 把 §5/§7/§8 的公式与**文档里给出的每一组数字**都跑出来对照，顺带把文档内部几处口径不一致标出来。

## 原理详解

### 1. 五个匹配条件（§4）

伪造应答要被接受，必须同时命中：

1. 强制解析器发出查询（§4.1）—— Kaminsky 的做法是不停查询目标域下不存在的随机名字；
2. Question Section 匹配（§4.2）；
3. **Query ID 匹配**（§4.3）—— 16 位，65536 种；
4. 源地址 == 真实权威服务器的地址（§4.4）；
5. 目的地址与端口 == 解析器发出查询时用的（§4.5），且**必须在真实应答之前到达**（§4.6）。

第 4 条意味着「域有几个权威服务器」直接决定难度：伪造包只能冒充其中某一个，所以问题空间要乘上 N。

### 2. 组合难度公式（§7.2）

设 `I`=ID 空间、`P`=可用源端口数、`N`=权威服务器数、`F`=窗口内到达的伪造包数、`R`=发包速率、`W`=窗口长度、`D`=相同在途查询数、`A`=尝试次数：

```
P_s  = D * F / (N * P * I)          F = R * W
P_cs = 1 - (1 - P_s) ^ A            A = T / TTL
```

代入文档列出的常用值（D=1、W=0.1、N=2.5、P=1、I=65536）化简为

```
P_cs = 1 - (1 - R / 1638400) ^ (T / TTL)
```

**1638400 = N·P·I/(D·W) = 2.5 × 65536 / 0.1**，本 demo 实测与此精确吻合。

TTL 为 0 的退化情形（§7.2）：攻击者用不断变换的查询让窗口随每个查询打开，此时**有效 TTL 就等于 W**。

### 3. 生日攻击（§5）

只要能迫使解析器对**同一个** (QNAME, QTYPE, QCLASS) 保持 D 个在途查询，每个伪造包就获得 D 倍的命中机会。文档明确说这个线性关系「only holds for small values of D」，所以本 demo 就是简单地把 P_s 乘 D，不做成 `1-(1-p)^D`。

### 4. 三档数字（§7、§8）

按文档口径复现，公式值与文档表述完全对得上：

| 场景 | 文档 | 本 demo 实测 |
| --- | --- | --- |
| 匹配 ID+地址平均包数（N=2） | 2 × 2^15 = 65000 | 65536（文档取整成 65000） |
| 65000 包塞进 100ms | 416 Mbit/s | 416.0 Mbit/s |
| 窗口放宽到 1 秒 | 42 Mbit/s | 41.6 Mbit/s |
| TTL=3600，7000 pps，24h | 10% | 0.0977 |
| TTL=3600，7000 pps，7 天 | 50% | 0.5129 |
| TTL=60，7000 pps，24 分钟 | 10% | 0.0977 |
| TTL=60，7000 pps，3 小时 | 50% | 0.5373 |
| TTL=60，7000 pps，9 小时 | 90% | 0.9009 |

注意 TTL=3600/24h 与 TTL=60/24min 的 `A` 都是 24，概率必然相同 —— 这不是巧合，而是公式只依赖 `A = T/TTL` 的直接后果：**降低 TTL 等价于等比加速攻击**。

### 5. 防御（§9）

- **§9.1 匹配规则**：源地址、目的地址、目的端口、Query ID、QNAME、QCLASS+QTYPE 全部对上才算数，任一不符即判无效。
- **§9.2 端口与地址随机化**：源端口取「尽可能大且不可预测」的范围（53 或 1024 以上），ID 用满 0–65535，多 IP 的解析器还应随机挑源 IP。这一条把问题空间放大 64000 倍。
- **§9.2.1 为什么不能用简单自增**：攻击者能迫使递归解析器向自己的权威服务器发查询，从而**测量**解析器的内部状态；常数、顺序递增、弱 PRNG 都能被预测，必须上密码学强度的 RNG。

## 关键代码

```python
def p_s(fake_packets, ns_count=2.5, ports=1, id_space=65536, outstanding=1):
    """单次窗口内被投毒的概率 P_s = D*F/(N*P*I)。"""
    return outstanding * fake_packets / float(ns_count * ports * id_space)

def p_cs(period_s, ttl_s, rate_pps=None, window_s=0.1, ns_count=2.5, ports=1,
         id_space=65536, outstanding=1, p_single=None, attempts=None):
    """P_cs = 1 - (1 - P_s) ** A，A = T/TTL；TTL=0 时有效 TTL 取 W。"""
    if p_single is None:
        p_single = p_s_from_rate(rate_pps, window_s, ns_count, ports,
                                 id_space, outstanding)
    if attempts is None:
        eff_ttl = ttl_s if ttl_s else window_s
        attempts = period_s / float(eff_ttl)
    return 1.0 - (1.0 - p_single) ** attempts
```

## 性能与边界

- **P_s 必须远小于 1**：公式 `P_s = D·F/(N·P·I)` 是概率的线性近似，当 `F` 大到接近问题空间时会算出 >1 的值。真实实现要夹到 1，本 demo 不做夹取以便直接对照文档。
- **D 的线性放大只在小 D 成立**：D 很大时（§5 末句"For larger numbers, this effect is less pronounced"）应当换成 `1-(1-p)^D`。
- **时钟口径**：`A = T/TTL` 是浮点除法，实际窗口数是 `floor(T/TTL)`，两者在 T 不是 TTL 整数倍时差一个窗口；文档没说取整方式，本 demo 用浮点。

## 注意事项与常见坑

1. **§8.1 的「7 秒 / 116 小时」用的是 N=1，不是 §7 默认的 N=2.5**。两个数字都只有把 N 取 1 才对得上（实测 6.45 s / 115.4 h；取 2.5 则是 16.2 s / 288.4 h）。文档在 §7.1 把 N 的平均值写成 2.5，到 §8.1 计算时却按单个权威服务器算 —— 这是**文档内部的口径不一致，本 demo 记录不改正**。
2. **§7 的「4 Mbit/s 达 50%」是线性近似**。60 分钟 + TTL=300 意味着 A=12，文档把 42 Mbit/s 直接除以 12 得到 ~3.5 再取整成 4；但用 §7.2 的精确公式反解，50% 需要 **5.89 Mbit/s**（4.37 Mbit/s 才能让线性值 `12·P_s` 恰好等于 0.5）。差别来源于 `(1-p)^A` 与 `1-A·p` 的差距。
3. **§8 的「285 Gb/s」不是从 416 Mbit/s 推出来的**：416 Mbit/s × 64000 = 26.6 Tb/s，差 93 倍；而 285 Gb/s ÷ 64000 = 4.45 Mbit/s，与 §7 那个多次尝试场景的 4 Mbit/s 才是同一口径。读文档时不要把这两个数字接在一起。
4. **「降低 TTL 能防投毒」是反的**：从公式看 P_cs 只依赖 `A = T/TTL`，TTL 越小 A 越大，同等时间内被投毒的概率**越高**。文档原话是「only raising the TTL offers protection」。
5. **端口随机化会被防火墙挡住**：§8 末句提醒，只放行单一 DNS 源端口出站规则的防火墙需要重新配置，否则解析器实际上退回到 P=1。
6. **65000 与 65536 别混用**：文档用 `2 × 2^15 = 65000` 是个取整表述，精确值是 `N·I/2 = 65536`（N=2）。用 65000 去算带宽得到 416 Mbit/s，用 65536 会得到 419.4 Mbit/s —— 断言时必须指定用哪一个。
