# 12 项目工程

> 项目工程（Software Engineering Practice / Codebase Craft）：研究**如何让一个大型代码库长期活得下去**——
> 从数据结构与容器的选型代价，到设计模式与架构边界，再到可读性、可测试性、依赖治理与度量门禁，
> 最后落到遗留系统的演进式重构。答案是「为什么这么写更好维护」，而不是「这样能跑」。
> 2026-09-22 用户指定新增顶层类目（横切学科，与按领域的 01-08、按语言的 09 互补）。

## 待研究

- [x] 容器选型的代价模型：同一操作在 1e3 / 1e6 量级下，常数因子与缓存未命中如何盖过渐近复杂度 → 见 [01-数据结构与集合选型](./01-数据结构与集合选型/) 首批 5 demo
- [x] 摊销复杂度陷阱：`vector` 扩容、`HashMap` 树化与 rehash 的瞬时尖峰在延迟敏感场景的后果 → 见 660/661/664
- [ ] 并发容器的代价：锁分段 vs 无锁队列在真实竞争度下的吞吐与尾延迟分水岭
- [ ] 「可维护性」的可度量化边界：哪些维度能进 CI 门禁、哪些只能靠评审
- [ ] 语言特性对设计模式的替代：一等函数/模式匹配/泛型分别吞掉了哪些 GoF 模式
- [ ] 分层架构「跳过一层」的取舍：何时该允许、如何防止退化成面条
- [ ] 包设计原则的可操作化：不稳定度 I = Ce/(Ce+Ca) 怎么在 CI 里算并设阈值
- [ ] 复杂度度量的口径差异：圈复杂度 vs 认知复杂度（Sonar 定义）在真实代码上的分歧点
- [ ] 覆盖率作为质量指标的失效模式：行覆盖 90% 但突变得分 40% 的代码长什么样
- [ ] 遗留系统 seam 识别：如何从调用图/数据依赖里找出「最小代价可替换边界」
