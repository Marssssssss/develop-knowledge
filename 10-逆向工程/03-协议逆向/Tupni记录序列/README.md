# Tupni：从执行轨迹里挖出记录序列、记录类型与约束

> W. Cui, M. Peinado, K. Chen, H. J. Wang, L. Irun-Briz, *Tupni: Automatic Reverse Engineering of Input Formats*, **ACM CCS 2008**。相比 AutoFormat 的"结构"，Tupni 多给三样东西：**记录序列（record sequence）、记录类型（record type）、输入约束（constraint）**——后者让它能直接服务 **0day 漏洞签名生成**，这是此前工具做不到的。

## 一、简介

Tupni 同样是 ExeT-based（拿二进制的执行轨迹），但目标不同：它要输出的格式描述除了字段，还包括

- 哪些字段构成一个**记录**、记录排成什么**序列**；
- 记录有哪几种**类型**（通常对应实现里的不同 handler 函数）；
- 输入必须满足的**约束**（单值谓词、函数式关系如校验和、跨报文依赖、长度字段）。

论文在 10 种格式上评测（WMF/BMP/JPG/PNG/TIF 五个文件格式 + DNS/RPC/TFTP/HTTP/FTP 五个网络协议），**识别出了测试输入中所有的记录序列**；并展示了把多个 WMF 文件聚合后能得到更完整的规范。

## 二、原理详解

流水线：`原始输入 → 基本字段 → 记录序列 → 记录类型 → 约束`。论文强调**每个阶段都是"基线算法 + 纠错方案"**的组合——基线抓住主要思想，纠错处理真实程序不遵守基线的情况。

### 2.1 chunk 识别（§3.3）

观察 CPU 指令的**操作数**：把操作数里**被污染的、偏移连续的最长字节序列**定义为一个 **chunk**。

- **忽略 mov 指令**——它不处理操作数，不含字段尺寸信息（与 AutoFormat 的处理一致）；
- chunk 的**权重 w(c) = 执行轨迹里访问它的指令条数**；
- 由此能识别 8/16/32/64 位整数与浮点 chunk，若看到**字节逆序**还能认出大端整数；
- 一个操作数里若有多段不连续偏移，会拆成多个 chunk。

论文自述局限（也是本目录下一个 demo 的动机）：

> "Currently we track input chunks at **byte granularity**; we believe it takes only engineering efforts to refine this to bit granularity."

### 2.2 纠错：加权 Maximum k-Set Packing（§3.3.1）

难点：同一偏移可能被不同类型的操作数访问，于是落进多个 chunk。典型成因有两类：

1. **批量访问**（内存拷贝、校验和）——程序不关心字段边界地整段读；
2. **优化过的字符串处理**——用 32 位指令处理 ASCII/Unicode 字符串。

要找的是"**互不重叠、且权重之和最大**"的一致子集 —— 这正是**加权 Maximum k-Set Packing**。它在最坏情况下**连近似都不可解**；但真实轨迹里重叠很少，论文用**贪心**就够了。

本 demo 的夹具里，`(8,12)`（优化字符串访问，权重 3）会挤掉与之重叠的 `(8,16)`（真实 payload，权重 1），`(0,4)`（循环条件读了 4 次，权重 4）会挤掉覆盖整包的 `(0,32)`（批量访问，权重 1）——贪心的取舍被完整复现。

**从未被访问的区间**只能标记为 **virtual field**（程序没读，观察就没有任何信息）。

字符串被当作**常规的记录序列**处理，因此 Tupni **没有"字符串字段"**这个概念：每个字符先是一个字段，再在记录序列阶段被合成为字符串。

### 2.3 循环识别与迭代相关指令（§3.4.1–§3.4.2）

程序要处理**无界**的记录序列，就**必须用循环或递归**。Tupni 处理循环（递归被认为同理）：

- 在**控制流图上找环**得到循环，只考虑**单入口**的环；
- 把环里的指令映射回 EIP，在轨迹里标出该循环对应的子序列；
- **以入口点出现的位置切分迭代**。

**迭代相关指令** `Ii`：一条指令属于 `Ii`，当且仅当它在第 `i` 次迭代里访问了某个**其他迭代都没访问**的字段。

> **关键特例（论文原文）**："the last iteration of a loop is often not a true iteration, but only a check of the termination condition" —— 若 `In` 为空，就把循环当作只有 `n-1` 次迭代。本 demo 夹具里第 4 段迭代只有循环条件，于是 `n` 从 4 降到 **3**。

循环被称为 **iteration dependent**，当且仅当 `Ii ≠ {}` 对 `i ∈ {1..n-1}` 全部成立。

### 2.4 记录边界（§3.4.3，Figure 4）

算法要点：

1. 第一条记录的起点 = 第 1 次迭代里所有迭代相关指令访问到的**最小偏移**；
2. 记下"访问了这条记录首字段"的指令集合 `I`——启发式是**这些指令每次出现都很可能在访问某条记录的开头**；
3. 往后在每次迭代里找 `I` 中的指令，把它访问的偏移当作该记录的起点；
4. `ej = s(j+1) - 1`；`en = max(Offset + sizeof)`。

> **Figure 4 的一处口径不一致**：第 17 行 `ej = s(j+1) − 1` 给的是**闭区间末字节偏移**，第 18 行 `en = Offset + sizeof` 给的却是**开区间右边界**，两者差 1。本 demo 把它写成断言（`e[0]+1 == s[1]` 且 `e[n-1] == 32`），换算回半开区间后记录区间与真值一致。

论文还坦承末记录的 `en` **可能偏小**（因为它只看迭代相关指令访问到的最后字节）。

### 2.5 记录类型（§3.5）

两条记录同类 ⟺ 处理它们的循环迭代**执行了"大体相同"的指令**（直觉：实现通常给每种记录类型一个独立的 handler）。

难点是**记录序列可以嵌套**：若一条记录里含子记录序列，那么同类型的两条记录其指令集合也可能差别很大——**直接比指令序列不行**。

解法：把 **Qi** 里属于**某次子循环执行**的整段**折叠成一条虚指令（virtual EIP）**。两条虚指令的标识相同 ⟺ 它们对应同一个循环的执行。于是

```
Q'i  =  Qi  把子循环执行段替换为该子循环的虚指令标识
Q'i == Q'j   ⟺   记录 i、j 同类型
```

净效果是：**子循环"是否被执行"重要，"执行了什么"不重要**。

### 2.6 约束（§3.6）

| 类型 | 含义 | 用途 |
| --- | --- | --- |
| 符号谓词（单值） | `f(input[i]) {<,=,>,≠} y`，`f` 只依赖输入值与硬编码常量 | 字段取值范围 |
| 函数式约束 | `input[x] = f(input[y], input[z], …)` | 抓住多数**校验和** |
| 跨报文依赖 | tainted 数据出现在外发报文里 → 输出数据流图 | 会话 ID、序列号 |
| 长度字段 | 三种技术：平台函数语义、用于计算访问指针的字段、用于计算循环终止条件的字段 | 长度 |

论文明确指出**动态分析的通病**：一次运行得到的谓词可能只属于那个具体输入，不代表格式本身。

## 七、性能边界与注意事项

- **加权 k-Set Packing 不可近似**（最坏情况）；贪心能work是因为真实轨迹重叠少，不是因为它有近似比保证。
- **只看循环，不看递归**（论文把递归列为"相信同理"但未实现）。
- **要求循环按输入顺序处理记录**，不满足的循环被直接丢弃。
- **字节粒度**：bit 级字段（bitflag）无法处理，见下一个 demo。
- **约束可能过拟合单次运行**（动态分析通病）。

## 八、常见坑（本 demo 实跑暴露）

1. **循环条件指令必须出现在每次迭代的开头**，否则按入口点切分会把三条记录并进同一"迭代"（本 demo 第一版就是这样，导致 `I[0]` 为空）；
2. **Figure 4 的 `e` 两种口径差 1**（2.4）；
3. **贪心要按权重降序而非出现顺序**，否则低权重的大块（整包批量访问）会先入选，把真实字段全挤掉；
4. **virtual field 必须在 packing 之后补**，否则会被当成真字段参与后续迭代分析。
