# SCHEDULE_QUOTA.md — 定时巡检的定量推进规范

> 本文件定义每 2 小时一轮的自动巡检**「推进多少」**的定量规则。
> 配套文档:
> - `SEARCH_PROGRESS.md` — 轮询索引与状态
> - `OPTIMIZATION.md` — 资源硬约束(搜索次数、token 预算)
> - `AGENT_RULES.md` — Agent 行为规范

## 一、度量单位

**1 个新 demo = 1 个推进单位**。

> 1 个新 demo 指:新建一个含 `README.md` + 至少 1 个代码文件的子目录,例如 `01-游戏开发/01-服务端/网络编程/IO多路复用/epoll/`。

**为什么用 demo 数**:
- 与项目主目标「按领域沉淀原理级 demo」直接对齐
- 衡量直观(看 SEARCH_PROGRESS 的 demo 表即可)
- 不会出现「凑 KB/凑动作数」的反向激励

## 二、每轮结构:1 主 + ≤ 1 副

| 任务 | 数量 | 内容 |
| --- | --- | --- |
| **主任务 (M)** | **必 1** | 1 个新 demo(路径形式) |
| **副任务 (S)** | **≤ 1,可 0** | 三选一,见下表 |

**副任务 S 三选一**:

| 选项 | 何时用 | 例 |
| --- | --- | --- |
| S1 · 已有 demo 增强 | 上一轮写过同一领域,且有可补的 | `select/` demo 补 Rust 实现 |
| S2 · 目录结构补全 | 准备下一轮深挖,先把骨架建好 | 新建 `02-Web开发/02-后端/Node.js/` 子目录 + README |
| S3 · 索引/记忆同步 | 阶段收尾,补全索引 | 更新 SEARCH_PROGRESS、daily log 摘要 |

**每轮总动作数 ≤ 2**(1 主 + 至多 1 副)。

## 三、降级规则

- **上一轮已完成 ≥ 1 demo** → 本轮**主任务可降级为 S1/S2/S3** + 至多 1 个零碎动作(版本号微调、修正笔误等)
- **上一轮失败或被跳过** → 本轮**主任务必做**(M),不允许连续 2 轮无新 demo
- **同一领域连续 ≥ 5 轮无新 demo** → 强制切到下一个索引(避免卡死)

## 四、失败重试与回退

```
单轮失败 → 重试同一索引(最多 3 次)
连续 3 轮同一索引失败 → 跳过该索引,记入 failed_attempts,跳到 next_index + 1
连续跳过 5 个索引 → 暂停自动巡检,发出告警,等用户决策
```

所有重试 / 跳过都写入 `SEARCH_PROGRESS.md` 的「本轮状态」和「调度日志」。

## 五、长周期目标(可由 Agent 自查)

| 周期 | 下限 | 备注 |
| --- | --- | --- |
| 单轮 | 1 主 或 1 副(M/S 二选一) | 缺一不算「推进」 |
| 每天(12 轮) | ≥ 3 个新 demo | 受 8 小时休息影响,实际约 6-8 轮 |
| 每周 | ≥ 7 个新 demo | 每天保底 1 个 |
| 每月 | ≥ 25 个新 demo | 30 天 × 0.85 = 25.5,取整 |
| 全量 | 9 个领域 × 平均 8 个 demos ≈ 70+ | 见 INDEX.md 概览 |

**周/月度回顾**:每周末 / 月末,Agent 跑一次自查,把累计 demo 数 / 目标写入 `daily log`。

## 六、与现有硬约束的关系

`OPTIMIZATION.md` / `MEMORY.md` 里定义的资源上限**仍然有效**:
- 每轮:≤ 1 agentic_search, ≤ 3 WebSearch, ≤ 2 WebFetch, ≤ 1 新 demo
- 新 demo 单文件 ≤ 300 行
- 总 token 预算按既有规则

**本规范与硬约束是「下限 vs 上限」的互补关系**:
- 硬约束 = 不能超过(防过度)
- 本规范 = 不能太少(防敷衍)

## 七、调度日志模板(每轮末尾追加)

```text
| 时间 | 索引 | 主任务 | 副任务 | 推进 | 累计 demo | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| YYYY-MM-DD HH:MM | N | M=epoll demo | S3=索引同步 | +1 | 3 | 正常 |
```

「推进」列只算主任务的新 demo 数。副任务不计推进量。
