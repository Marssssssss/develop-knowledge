# 帧同步（Deterministic Lockstep）

## 简介

**帧同步（lockstep）** 是 RTS/MOBA/格斗类联网的经典模型：**服务器/各客户端不传单位状态，只广播玩家指令**，每台机器用同一份代码、同一份随机种子跑**完全相同的模拟**，从而各自算出同一个世界。

关键概念：

| 概念 | 含义 |
| --- | --- |
| **同时模拟（simultaneous simulation）** | 每台机器跑同一份模拟，同步游戏时钟与随机数发生器 |
| **通信回合（communication turn）** | 与渲染帧解耦的独立时间单位，AoE 里典型 **200 ms** |
| **2 回合前瞻** | 第 1000 回合发出的指令，预约在第 **1002** 回合执行 |
| **失同步（out-of-sync）** | 两台机器算出的世界不一致；靠逐回合**校验和**发现 |
| **确定性（determinism）** | 同一输入序列在任何机器上必须得到**逐位相同**的结果 → 用定点数 |

历史背景：Age of Empires（1996–1999）为实现「1500 个弓箭手 + 8 人联机 + 28.8k modem + P90」的目标而确立了这套模型。若改传单位状态（x, y, status, action, facing, damage），**最多只能支持 250 个移动单位**——远达不到设计目标，所以只能改成只传指令。

## 原理详解

### 1. 通信回合与 2 回合前瞻

```
通信回合      t-2        t-1         t         t+1       t+2
             ┌──────────┬──────────┬─────────┬─────────┬─────────┐
发出指令      │  发出     │          │         │         │         │
接收/存指令   │          │  到达     │         │         │         │
执行指令      │          │          │ 执行 ←──┼── 预约 ──┤         │
             └──────────┴──────────┴─────────┴─────────┴─────────┘
                            ↑  每个回合同时在做三件事:
                     「执行本回合 / 接收并存下回合 / 为 t+2 发指令」
```

- 回合长度 **200 ms**；回合结束时切断，开始下一回合；
- 指令「预约 2 个回合后执行」→ 链路延迟 ≤ 2 回合时 **2 回合前瞻全额吸收**，不产生卡顿；
- 延迟 > 2 回合 → 该回合只能等（`speed control` 会把通信回合拉长，代价是整体节奏变慢）。

本 demo 实测（3 peer / 12 回合）：

| 链路延迟（回合） | 执行回合数 | 起播延迟 | 卡顿次数 |
| --- | --- | --- | --- |
| 1 | 12/12 | 0 | 0 |
| 2 | 12/12 | 0 | 0 |
| 3 | 12/12 | **1** | **1** |

通信回合 3 上把 3 个 peer 的包全部丢弃（按 RTO 重传）：通信回合从 13 拉到 **15（+2）**、卡顿 1 次 —— 这就是 AoE 所谓的 **speed control**：宁可把回合拉长，也不让游戏卡在某一帧。

### 2. UDP 之上的「自建可靠」

- 传输层用 **UDP**；定序、丢包检测、重传**由每个客户端自己实现**；
- 每个包带 2 个字段：**预约执行回合号** + **消息序号**；
- 收到属于过去回合的包 → **直接丢弃**；
- 核心假设：**「When in doubt, assume it dropped」**（拿不准就当丢了）——收到乱序包立刻请求重传，**ack 迟到也直接重发**（不等请求）；
- 副作用：迟到重传会产生重复包，接收端必须自己幂等。

### 3. 失同步与校验和

每回合对世界做一次校验和（对象、寻路、目标选择……），任一回合不一致即判定 out-of-sync。难点在于**极小差异会随时间放大**：

> 「一只鹿在随机地图生成时略微错位 → 觅食路径略有不同 → 几分钟后村民的路线差了一点点，或者长矛刺空、没带回肉 → 校验和最终表现为食物数量不同。」

微软 PM 的原话：*「每个项目里都有一个顽固的 bug 会一直撑到上线——我觉得 out-of-sync 就是它。」* 当年为了查它得翻 **50 MB 的消息 trace**。

### 4. 为什么必须用定点数

帧同步的硬约束是 **逐位可复现**。本 demo 用「换一个求和顺序」来暴露浮点的问题：

| 模型 | 升序 vs 降序累加 1/(i+1) | 结论 |
| --- | --- | --- |
| `float64` | 第 **2** 回合即分叉：`5.435714285714286` vs `5.435714285714285`，差 **8.882e-16** | 顺序敏感 → 不可用 |
| Q16.16 定点 | `178117` vs `178117` | 整数加法与顺序无关 → 安全 |

同样的模拟，3 个 peer 逐回合比校验和：

| 场景 | 首次失同步回合 |
| --- | --- |
| 定点 + 全部同序 | **未失同步** |
| 定点 + peer2 **反向遍历** | **未失同步**（整数加法结合律） |
| 浮点 + peer2 反向遍历 | **第 2 回合** |
| 定点 + peer2 **多取一次随机数** | **第 1 回合** |

### 5. 随机数同步

- 必须有**同步的随机池**（同一 seed、同一取数次数）；
- AoE 实际上有**两个 RNG**：一个同步（战斗等影响玩法）、一个**不同步**（动画抖动等纯表现）。挑错池子就会导致失同步——原作者回忆：「动物的朝向看起来是动画，但它会影响能否被猎杀」；
- 「同一段代码必须调用**相同次数**的随机数」——这是当年最难接受的概念性约束之一。

## 对比 / 选型

| 维度 | 帧同步（lockstep） | 状态同步（server-authoritative） |
| --- | --- | --- |
| 传输内容 | 只传**指令**（每人每回合 1 个包） | 传**状态快照**（增量压缩） |
| 带宽 | 与玩家数相关，与单位数**无关** | 与实体数、变化频率相关 |
| 服务器权威 | 弱（可被改客户端作弊，但差异会被检出） | 强（服务器判定一切） |
| 断线重连/观战 | 难（要追帧重演） | 易（直接下快照） |
| 典型场景 | RTS / MOBA / 格斗 / 部分 MMO 战斗 | FPS / MMO 大世界 / 移动端 |
| 调试难度 | 高（失同步溯源极难） | 中 |

帧同步的两个变体：

- **Rollback（回滚网码）**：让远端输入固定在某个延迟下到达，必要时**回滚并重演**若干帧。GGPO 一系的「8 frames in 16ms」是这一路线的代表（见参考资料中的讨论串）；
- **乐观帧同步**：不严格等待全部指令，用「缺省指令」垫帧，牺牲确定性换手感。

while next_exec <= last_exec:

## 性能与边界

- **包量与单位数解耦**：这是帧同步最核心的收益。传状态时「x, y, status, action, facing, damage」6 个字段 × 250 单位 × 15 次/秒 ≈ **160 Kbps** 就已经顶到 28.8k modem 的天花板，只能支持 250 个移动单位；改传指令后（每回合 2 字节左右的 fps/rtt 开销 + 每人 1 个指令包）可以做到 **1500 个弓箭手**。
- **卡顿上限由最慢的机器决定**：lockstep 里只要一台机器变慢，所有人都得等。修复手段是 speed control：`通信回合长度 = 该周期内最慢机器平均能跑的模拟帧数`，且**升快降慢**（快速响应延迟抖动，缓慢回落）。
- **帧率与回合长度是两件事**：AoE 目标 15 fps（67 ms/帧）但通信回合 200 ms —— 一个回合里跑多个渲染帧。
- **确定性代价**：不能用 `-ffast-math`、不能依赖 FMA contraction / x87 80 位中间精度、不能依赖不同 libm 的 `sin/cos` 实现；轨迹、单位朝向、随机调用次数、浮点累加顺序都必须是输入的函数。
- **本 demo 规模**：3 peer / 12~20 回合 / 8 单位，纯内存模拟，毫秒级完成。

## 注意事项与常见坑

1. **浮点求和顺序不一致** —— 现象：两边起初完全一样，第 2 回合校验和就不同；原因：不同编译器/优化级别/向量化改变浮点归约顺序，`a+b+c ≠ a+c+b`；规避：改用 Q16.16/Q32.32 定点、整数化，并禁用 `-ffast-math`。
2. **改了定点却忘了统一舍入方向** —— 现象：改用定点后仍失同步；原因：`(-3/2) * (1/3)` 这类负值运算，「算术右移（向下取整）」得 `-32768`，「向零截断」得 `-32767`（本 demo 已实测分叉）；规避：跨端约定同一个 `mul/div` 舍入规则（通常统一为向零截断），并把它封成一个函数。
3. **随机数调用次数不一致** —— 现象：第 1 回合就崩；原因：一方进了 `if` 分支多抽一次随机；规避：RNG 调用必须是输入的纯函数，禁止在表现层（动画/特效）使用同步 RNG。
4. **两个 RNG 用错池子** —— 现象：偶发失同步，复现极难；原因：把「同步 RNG」用于纯动画、或把「不同步 RNG」用于影响玩法的逻辑（如动物朝向影响能否被猎杀）；规避：显式区分两个池子并在 code review 中强制检查。
5. **拿 UDP 当可靠传输用** —— 现象：偶发卡顿后回合被拉长；原因：没实现「拿不准就当丢了」的重传策略导致等 ack 超时；规避：按 RTT 动态设定重传超时，ack 迟到也直接重发（接收端靠序号幂等去重）。
6. **收到过期包** —— 现象：世界状态被旧指令污染；规避：包必须带预约执行回合号，早于当前执行回合的直接丢弃。
7. **把渲染帧当通信回合** —— 现象：帧率波动直接变成网络抖动、指令延迟剧烈变化；规避：两者解耦，通信回合独立计时。
8. **断线重连/中途加入很难** —— 帧同步不保存世界快照，新加入者只能从头重演（追帧）。这是该模型相对状态同步的结构性劣势，需要额外的「快照 + 增量重演」机制。
