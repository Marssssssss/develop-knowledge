# Little 定律与排队守恒

> 容量规划里唯一**不需要任何分布假设**的那条公式就是 `L = λW`。本 demo 把它做成一个可执行的守恒律：给你任意两个量能求第三个，用 M/M/1 的解析解核对它在排队系统上精确成立，再用一个**事件驱动仿真**验证「即使在随机到达 + 随机服务的真实队列里，时间平均的在系统中数量仍然等于到达率乘平均逗留时间」。

代码：`python/little.py`（模型 + 仿真）、`python/selfcheck_little.py`（49 条断言）、`python/main.py`（演示入口）、`go/`（同口径 Go 实现）。

## 一、Little 定律：三个方向各用一次

```text
L = λ × W
```

- **定并发（sizing）**：λ = 500 rps、W = 200 ms → `L = 100`。池子给 100 才够，给 90 就开始无界排队。
- **找隐性等待**：L = 50、λ = 100 rps → `W = 500 ms`。若服务时间只有 50 ms，那么 **450 ms 全在排队**——这段等待没有任何 profiler 能看到，因为**没有代码在跑**。这是排队论给工程实践最实用的一条推论。
- **算吞吐上限**：单 worker 一次只处理一个请求、S = 10 ms → 上限 `1/S = 100/s`。想更高只有加并发或并行。

配套的**利用率定律** `U = λS/m`：单服务台时 `U = ρ`，也就是说「利用率」不是仪表盘上独立的第三个量，它就是 λ 和 S 的乘积。

实现上三个方向共用一个函数（已知两个、缺省那个）：

```python
little_l(lam=500, W=0.2)   # -> 100.0
little_l(L=50, lam=100)    # -> 0.5
little_l(L=100, W=0.2)     # -> 500.0
```

## 二、M/M/1 的四个稳态量

`ρ = λ/μ`，且**必须 `ρ < 1` 才稳定**（代码里直接抛 `ValueError`，这是模型唯一不能越过的边界）：

```text
W  = 1/(μ − λ)        Wq = ρ/(μ − λ)
L  = ρ/(1 − ρ)        Lq = ρ²/(1 − ρ)
π_k = (1 − ρ)ρ^k
```

Little 定律在 M/M/1 上不是近似，而是**代数恒等式**，所以可以直接断言到 `1e-9`：

```python
abs(m.lam * m.W  - m.L ) < 1e-9      # λW   = ρ/(1−ρ)
abs(m.lam * m.Wq - m.Lq) < 1e-9      # λWq  = ρ²/(1−ρ)
abs(m.W - (m.Wq + m.S)) < 1e-9       # W    = Wq + S
abs(m.L - (m.Lq + m.rho)) < 1e-9     # L    = Lq + ρ
```

## 三、拐点：延迟是「剩余余量」的函数，不是负载的函数

`W/S = 1/(1 − ρ)`。实跑输出（S = 100 ms）：

| ρ | 倍率 | W |
| --- | --- | --- |
| 0.10 | 1.11× | 111.1 ms |
| 0.50 | 2.00× | 200.0 ms |
| 0.70 | 3.33× | 333.3 ms |
| 0.80 | 5.00× | 500.0 ms |
| 0.90 | 10.00× | 1000.0 ms |
| 0.95 | 20.00× | 2000.0 ms |
| 0.99 | 100.00× | 10000.0 ms |

两个被断言钉死的比例关系：**70% → 80% 要多付 50% 延迟**（500/333.3 = 1.5），**90% → 95% 再翻倍**（2000/1000 = 2.0）。所以容量目标落在峰值 60%–70% 不是玄学，是这条双曲线在拐点左侧的余量。

## 四、死队列：为什么有界队列是必需品

`dead_queue(depth, drain_rate, timeout)` 按入队顺序排空：第 `i` 个元素在 `t = i/drain_rate` 完成，**严格小于** `timeout` 才算有效（恰好等于超时时刻视为作废——调用方已经放弃）。

实跑：`depth=10000, drain=500/s, timeout=2s` → **作废 9000、有效 1000**，第一个作废请求恰好等到 2.0 s。也就是说系统处在 100% 利用率上，但**产出只有十分之一**——这正是「有界队列 + 快速失败」存在的理由：宁可早一点拒绝，也不要把资源花在注定超时的请求上。

## 五、用仿真核对守恒律

解析公式是相信别人推导的结果；仿真是让随机过程自己把 `L = λW` 走出来。`simulate_mm1` 是一个最小事件驱动循环（指数到达 / 指数服务，固定种子）：

- `L̂`：时间平均（面积/时长）
- `λ̂`：**离开**计数 / 时长（用离开而非到达，保证 `L̂` 与 `Ŵ` 统计的是同一批请求）
- `Ŵ`：**已完成**请求的平均逗留时间

实测（t = 20000 s，约 1000 万个请求）：

| λ | ρ | L̂ | λ̂·Ŵ | 解析 L |
| --- | --- | --- | --- | --- |
| 500 | 0.5 | 1.0016 | 1.0016 | 1.0 |
| 800 | 0.8 | 4.0129 | 4.0129 | 4.0 |

断言口径：`|L̂ − λ̂Ŵ| / L̂ < 2%`（ρ=0.8 时放宽到 3%，因为排队越深方差越大）。另外同种子两次仿真结果必须**逐位相同**，否则断言本身不可信。

## 六、踩过的坑

- **死队列的边界是「严格小于」还是「小于等于」，会整整差一个元素**。`depth=1000, drain=500, timeout=2` 时第 1000 个元素恰好在 2.0 s 完成：按 `<=` 算它是有效的（作废 8999），按 `<` 算它已作废（作废 9000）。本 demo 采用 `<`（与「超时即放弃」的语义一致），并把这个边界单独做成一条断言。
- **仿真的 λ̂ 必须用离开计数而不是到达计数**。用到达计数时，系统里滞留的那部分请求会让 `λ̂W` 系统性大于 `L̂`，ρ 越高偏得越明显。
- **`1/(1−ρ)` 在 ρ→1 时发散**，任何「按 99% 利用率规划」的推演都会算出荒谬的排队长度——这不是模型坏了，是模型在告诉你这个点不能待。
