# 观察者与事件分发(pub/sub 的两个刻度)

> 观察者的定义只有两句话:**发布者持一张可增删的订阅者名单,事件发生时经统一接口逐个通知**。
> 名单放在发布者自己身上是经典观察者;把名单抽给中间人按主题路由,就是发布订阅。
> 同一个机制的两种部署刻度。

## 1. 订阅机制两要素(refactoring.guru Observer 页)

```text
publisher: { subscribers: [Subscriber...] }
           subscribe(sub) / unsubscribe(sub) / notify(event)
Subscriber 接口: update(event)——发布者与订阅者只经此接口相识
```

- 名单**运行时动态**:对象随时开始/停止收通知;
- 新增订阅者类型不需要改发布者(接口是唯一耦合点);
- 发布者可将自己作为事件上下文传入,订阅者按需拉取数据。

## 2. 实现陷阱:通知循环里退订

通知时遍历的必须是**名单快照**:本轮已订阅者全部收到,退订下一轮生效。
边遍历边删原列表会跳项——观察者实现里最高频的 bug。

## 3. 演化路径:集中分发器

页面原文的升级方向:把订阅管理委托给专职对象,"升级为集中式事件分发器,
让**任意对象**都能当发布者"。此时:

| | 观察者 | 发布订阅(pub/sub) |
| --- | --- | --- |
| 名单在哪 | 发布者自己身上 | 中间分发器 |
| 双方关系 | 订阅者认识发布者 | 互相不认识,只认主题名 |
| 路由 | 直连 | 按主题/事件类型 |

## 4. 解耦的代价(为什么"隐式控制流"是双刃剑)

- 调用点看不到谁在听、几个在听、订阅者抛异常会怎样;
- 事件链一长(订阅者再 emit),因果要靠事件日志才能拼出来;
- 退订遗漏 → 幽灵订阅者/内存泄漏(弱引用是一种对策,但引入"对象还活着吗"的新问题)。
