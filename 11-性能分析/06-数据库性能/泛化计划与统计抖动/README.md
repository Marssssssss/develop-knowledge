# 泛化计划与统计抖动(PREPARE 的计划翻转)

> prepared statement 的计划缓存有自己的一套决策:**前五次定制、之后择机泛化**。
> 参数分布偏斜时,"择机"会切到一条对常见值好、对偏斜值灾难的计划——
> 同一条语句、同一份数据,某天突然慢了,先查这里。

## 1. 泛化 vs 定制(官方 sql-prepare.html 口径)

- **泛化计划**:全部执行共用一条,省规划开销;参数以平均面目参与估算;
- **定制计划**:按本次参数值规划,可用值的选择率信息选路;
- 语句**没有参数**时,这个争论不存在——永远泛化。

## 2. auto 模式的五次规则

```text
第 1~5 次执行:定制计划,记录各次的估算代价
第 6 次起:生成泛化计划,代价与「前五次定制平均代价」比较
          泛化代价不高于平均太多 → 用泛化;否则继续每次定制
```

- 比较的具体倍数官方文档未公布,只说 *not so much higher*(本 demo 以可配置系数建模并标注);
- `plan_cache_mode = force_generic_plan / force_custom_plan` 可强制;
- **判别现场**:`EXPLAIN EXECUTE` 里泛化计划显示 `$1` 占位符,定制计划显示代入后的字面值;
- 会话内所有 prepared 语句可查 `pg_prepared_statements` 视图。

## 3. 经典翻转回归(偏斜参数)

```text
训练期:参数全是高选择性的常见值 → 定制计划便宜 → 平均价低
第 6 次:泛化计划 ≈ 平均价 → 切换成功
之后:罕见的偏斜值到来(如 status='pending' 占 99% 的列查 'failed')
      泛化计划按平均选择率估行数 → 选错扫描方式 → 突然慢百倍
```

应对方:`plan_cache_mode=force_custom_plan`、SQL 改写绕过参数化、
或对偏斜列单独处理(MCV 会救一部分,但泛化计划根本不看值)。

## 4. 强制重规划的三个触发条件

即使已经切到泛化计划,以下变化会**强制重新分析并重规划**:

1. 语句引用对象发生 **DDL 定义变更**;
2. **规划器统计信息被更新**(ANALYZE/autovacuum 触发的统计刷新);
3. **search_path 变化**(9.3+,按新 search_path 重新解析)。

所以统计抖动会传染给 prepared 语句:一次 ANALYZE 可能让同一条语句
在下一次执行时换计划——配合第 3 节,构成"没有任何代码变更却变慢"的完整解释链。
